# NCP 운영 준비 점검표

이 문서는 확인 절차이며 운영 DB 마이그레이션·배포·자동 동기화 활성화 지시가 아니다. 현재 NCP 실서버에서 아래 항목의 검증을 완료하지 않았다.

## 현재 운영 적용을 막는 요소

1. 실제 서버 OS·컨테이너·볼륨·DB 연결 세션의 운영 설정을 확인하지 못했다.
2. 확보한 공식 개장일 대조 파일은 2023-10-27~2026-10-29 범위다. 운영에 필요한 과거 여유 범위와 미래 일정, 변경일 종료 시각의 검증·연결이 필요하다.
3. 운영 DB의 실제 스키마 차이·데이터 분포·시간대를 조회하지 않았다. 저장소 전체 DDL + 합성 데이터 검증을 운영 복사본 검증으로 표현하지 않는다.
4. 실제 서버 간 HTTP·서비스 주소·재기동·장애 복구와 현재 배치의 KIS 호출량·소요시간을 실측하지 않았다.
5. 자동 동기화는 기본 false다. 초기 주기·재시도·마감 값은 개발 기본값이며 운영값 확인이 필요하다.

## 점검표

| 항목 | 승인 전 확인할 내용 | 현재 상태 |
|---|---|---|
| OS·배포 구성 | NCP OS, Docker/Compose 버전, 실제 앱·배치 실행 주체, risk 서비스 정의 확인. CI ubuntu-latest를 서버 OS로 취급하지 않음 | NCP 미확인 |
| SQLite 영속성 | API와 배치가 같은 영구 DB 파일을 사용. 컨테이너 재생성 후 등급·가격·버전·실행 이력 보존 | 서버 미검증 |
| 파일시스템·권한 | DB와 journal 등 부속 파일을 다룰 디렉터리 권한·UID/GID·용량 확인. 네트워크 파일시스템은 잠금 보장을 별도 검증 | 서버 미검증 |
| 배치 잠금 | 한 DB에 한 쓰기 배치. 컨테이너 간 같은 잠금 파일/inode 공유, 강제 종료 후 재개, 살아 있는 잠금 파일 삭제 금지 | 로컬 검증, 서버 미검증 |
| SQLite 읽기·쓰기 | API 조회 중 게시, 중단 후 journal 복구, 잠금 대기·실패 처리 확인. WAL 등 저장 모드를 임의로 변경하지 않음 | 원자적 저장·읽기 로컬 검증, 서버 journal 장애 복구 미검증 |
| 백업·복원 | SQLite 일관된 백업과 복구, 게시 버전 고수위·이력 보존. 오래된 백업으로 복원한 뒤 버전이 역행하지 않도록 게시 재개 조건 확인 | 운영 복원 미검증 |
| 공식 달력 | 휴장일·변경 종료 시각·출처와 범위, STALE 종목의 공통 3년 구간 및 직전 가격일까지 확보, 미래 갱신 알림 | 자료 보강 필요 |
| 달력 동일성 | 두 컨테이너에 동일 CSV 바이트를 배포. Python calendar-status 결과와 MARIA expected-calendar-version 비교. GET /grades만으로 Python 현재 달력 해시를 확인할 수는 없음 | 합성 공유 파일 검증 |
| 시간대 | 실제 시장 시계 KST·호스트 시계 동기화·JDBC 세션 +09:00 확인. 공용 풀 변경 전 기존 SYSTEM_CLOCK 영향 검토 | 로컬 KST/UTC 조합 검증 |
| 내부 HTTP | MARIA→Python GET /grades와 패키지 요청, 연결/읽기 타임아웃·실패 후 회복. 키·환경 파일·DB 파일을 공개하지 않음 | 등급 로컬 실제 HTTP 검증, 패키지 서버 간 HTTP 미검증 |
| MARIA 실행 잠금 | 모든 인스턴스가 같은 쓰기 DB의 이름 잠금·상태 행 사용. 읽기 복제본/다른 DB 서버로 분산하면 동일 잠금이라고 가정하지 않음 | 단일 임시 서버 다중 연결 검증 |
| 커넥션 풀 | Pull 실행 잠금 연결과 종목별 저장 연결의 여유, 장시간 HTTP·DB 연결 단절·서버 전환 시 복구 확인 | NCP 미검증 |
| Python 외부 스케줄러 | 실제 OS에 맞게 기존 CLI 실행. 정상일 종료+10분, 변경일·휴장일 처리, 중복 실행·중단 후 기준일 고정 재개 | 미등록 |
| MARIA 주기·재시도 | 5분 주기와 장애 재시도의 구분, 일부 종목 게시 후 계속 조회, 중복 실행 차단, 다음 거래일 재개·마감 확인 | 로컬 검증 |
| DB 적용 | 보존 마이그레이션 백업·유지보수·재실행 계획. DDL 전체 롤백을 보장하지 않음. 이관 버전 0은 검증 게시 전 사용 차단 | 임시 전체 구조 검증 |
| 관측·사용 경로 | 동기화 실패·만료·버전 충돌·달력 부족을 구분. 모든 소비자가 공통 유효성 서비스를 사용 | 현재 코드 확인, 실제 소비 기능 추가 시 재확인 |
| 활성화 | 아래 조건을 충족하기 전 RISK_SYNC_ENABLED=false 유지 | 비활성화 유지 |

## 설정과 활성화 조건

현재 개발 기본값은 정상 조회 PT5M, 장애 간격 PT1M, 추가 재시도 3회, tick 30초다. cutoff-after-close=PT0S는 같은 날 KST 자정까지이며 양수는 실제 종료 이후의 조기 마감이다. 운영 마감은 별도 확인한다. Python 수집·계산을 동기화 재시도 때문에 다시 실행하지 않는다.

활성화에 앞서 운영자 승인, 보존 마이그레이션 검증, DB 세션 시간대, 동일한 공식 달력·충분한 범위, 실제 HTTP 연결과 실패 복구, 중복 실행 방지, 초기 게시 버전 1 이상 수신·만료 차단을 확인한다. 운영 DB 이관과 실제 배포는 별도 승인 단계다.

위험등급 세션만 KST로 맞추는 구성을 검토할 수 있으나 현재 운영 코드가 별도 위험등급 DataSource를 자동 구성하는 것은 아니다. 공용 풀의 시간대를 무심코 바꾸면 기존 업무시계가 달라질 수 있다. 운영 연결 설정 확인 후 필요한 설정·코드 범위를 먼저 보고한다. 추가 테이블·컬럼 변경은 현재 계획에 없다.

## 문서 공유

기존 docs/RISK_VALIDATION.md와 docs/RISK_INTEGRATION.md는 로컬 `.git/info/exclude`의 docs/ 규칙으로 제외돼 있다. 이는 Git으로 공유되는 .gitignore 규칙과 다르며 제외 의도는 코드만으로 확정할 수 없다.

이 integration/risk/ 경로의 문서는 민감정보 없이 계약·절차·검증 한계만 정리한 팀 공유 후보다. 기존 제외 규칙을 바꾸거나 강제 추가하지 않았다. 팀은 사용자가 검토 후 이 경로를 커밋하거나 팀 문서 저장소에 게시하는 방식으로 공유할 수 있다. 자동 커밋·외부 전송은 하지 않았다.
