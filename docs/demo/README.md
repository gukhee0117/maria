# MARIA 라이브 시연 — 실행 가이드

`demo-scenario.http`(IntelliJ HTTP Client)와 `demo-seed.sql`로 구성된 1차 시연용
런북. "고객의 실제 요청은 없지만 있다고 치고" 관리자 화면 뒤에서 실제 API가
계좌 개설부터 세액계산·인출까지 전부 흐르는 걸 보여주는 게 목적.

**2026-08-20에 `customer_id=18001` / `account_id=502`로 A1~A18, B2~B6, B8~B11
전부 라이브로 실행 완료.** 매 단계 손계산과 API 응답이 소수점까지 정확히
일치하는 것까지 확인함. 아래 "실측 결과"와 "실행 중 발견한 것" 참고.

## 선행 조건

1. **인출 API** — 처음엔 `WithdrawalApi`에 `POST /api/withdrawals`가 없었는데,
   upstream PR #205(gukhee0117, `[FEAT] 인출 요청 API 및 응답 정보 개선`)로
   추가됨. 반영 후 앱 재시작(devtools 핫리로드가 컨트롤러 추가를 못 잡음 —
   프로세스를 완전히 죽였다 `./gradlew bootRun`으로 다시 띄워야 반영됨).
2. `maria`, `mydata`, `return-securities` 세 애플리케이션이 각자 DB에 붙어 기동 중이어야 함.
   이 저장소는 `docker-compose.yml`이 없어서 DB(MariaDB `mariadb` 컨테이너,
   PostgreSQL `stockflow-postgres` 컨테이너)는 팀원이 직접 `docker start`로
   띄워야 함.
3. `demo-seed.sql`의 0-1~0-3을 먼저 실행 — `customer_id=18001`에 보유종목을 심어야
   입고 단계가 의미 있는 값을 냄.
4. `admin_user` 로그인 비밀번호는 팀 공유 값 사용 (해시만 커밋되어 있어 평문은 코드에 없음).

## 왜 customer_id=18001인가 (게으른 방법 vs 제대로 된 방법)

`seed-generator`가 만든 `db/seed/*.sql`은 이미 `account_id=1..18000`에 계좌를
전부 만들어놨고, `registrable_stock`도 그중 OPENED 상태인 사람한테만 짝지어
심어놨다. 즉 **"계좌 없고 보유종목만 있는" 깨끗한 상태의 고객이 벌크시드엔 없음**.

- **게으른 방법**: 이미 OPENED인 기존 계좌(`account_id=1` 등)를 그냥 재사용.
  계좌 신청/승인 단계는 건너뛰고 매도부터 보여줌. 리허설 중 시간 없을 때 씀.
- **제대로 된 방법(이 런북의 기본값)**: `ACCOUNT_COUNT` 다음 번호(`18001`)를 골라
  `registrable_stock` 한 줄만 얹고, **계좌 신청 → 승인부터 전부** 라이브로 보여줌.
  §10 데모 전략의 "매도차익 있는 해외주식 편입" 시나리오를 처음부터 재현하는 쪽.

두 방법 다 `db/seed/*.sql`을 다시 만들거나 대량 데이터를 새로 생성하지 않는다 —
이미 있는 3만 명 풀(§12 population→customer→general_customer 파이프라인)에서
번호 하나만 골라 쓰는 것뿐.

## 실측 결과 (2026-08-20, account_id=502)

세 구간 매도를 실제로 체결·확정산한 값을 손계산과 대조 — 전부 소수점까지 일치.

| 구간 | 매도 | 확정금액(원) | 매입원가(원) | 양도소득(원금액) |
|---|---|---|---|---|
| 1차(100%, 3/30) | 40주 | 18,767,976 | 5,400,000 | 13,367,976 |
| 2차(80%, 6/15) | 20주 | 9,362,906 | 2,700,000 | 6,662,906 |
| 3차(50%, 8/15) | 3주 | 1,316,263 | 405,000 | 911,263 |
| 4차(50%, 8/18) | 1주 | 437,452 | 135,000 | 302,452 |

- 외부순매수 반영 전: `weightedSell=26,916,432.30`, `adjustRatio=1.0000`, `finalTax=0`
- myData에 AAPL 2천만원 매수(6/15) 주입 + 동기화 후: `weightedExternalAmount=18,470,019.00`
  (기존에 이 고객한테 있던 실거래 이력 ARKK/IWM/XLF/SOXX까지 같이 잡힘),
  `adjustRatio=0.3138`, `finalTax=2,734,961.03`. 이 시점 `account.benefit`이
  `POSSIBLE → REDUCED`로 **자동 전환**되는 것도 확인(원래 몰랐던 부수 기능).
- 조기인출(2천만원, 미경과 원금) 후: `adjustRatio=0.0000`, `finalTax=4,123,811.34`
  ((21,244,597−2,500,000)×22%), `benefit`은 `REDUCED → IMPOSSIBLE`로 전환.
  배분은 FIFO로 `left_amount` 143(1차분 18,767,976 전액) → 144(2차분 중
  1,232,024)까지 정확히 2천만원 채움.

## 실행 중 발견한 것 (시연 리허설 시 주의)

- **매도는 실제 오늘(달력 기준)보다 미래 날짜로 못 함.** `SellOrderServiceImpl`이
  기준가를 한국투자증권 실시간 API(`KisPriceClient`)로, 확정산은 실시간 환율
  API로 조회하는데 둘 다 미래 시세/환율이 없어서 타임아웃/에러가 난다. 이건
  버그가 아니라 "우리가 진짜 외부 API를 부른다"는 증거라 오히려 좋은 시연
  포인트 — 다만 시연 중 시스템 시각을 실제 오늘 이후로 올리면 절대 안 됨.
  (인출은 KIS/환율 API를 안 부르므로 이 제약이 없음 — 매도결제일로부터 1년
  경과한 "정상 원금 인출"을 보여주려고 2027년으로 시계를 돌려도 될 것으로
  보이나, 오늘은 조기인출만 확인함.)
- **확정산 배치는 영업일 단위 idempotency 가드(`settlement_batch_guard`)가
  있어서, 이미 팀이 예전에 써버린 영업일(이 DB엔 3/30, 3/31, 6/16, 8/16, 8/17,
  8/18, 8/19가 이미 소비됨)로 다시 이동하면 새 매도건이 있어도 배치가 스킵된다.**
  시연 전에 `SELECT business_date FROM settlement_batch_guard;`로 미사용
  영업일을 확인하고 그 날짜를 써야 함.
- **비동기 배치와 조회 사이에 타이밍 레이스가 있다.** `/api/tax/snapshots/jobs`,
  `/api/settlement/jobs`, `/api/external-trade-sync/jobs` 전부 즉시 "REQUESTED/
  RUNNING"만 응답하고 실제 처리는 비동기로 늦게 끝난다. 바로 이어서 조회하면
  옛날 값이 나올 수 있음 — 3~5초 정도 텀을 두거나, 동기 계산인 `/api/tax/preview`로
  먼저 확인하고 배치는 나중에 재조회하는 식으로 시연할 것.
- **"개설 후 사후 초과 감지"는 코드에서 못 찾음.** §2 표엔 "합계가 5천만원 초과
  시 초과 시점 개설한 계좌는 통째로 세제혜택 배제"라고 되어 있는데, `applyAccount`/
  `approveAccount` 둘 다 신청·승인 **시점에** `validateLimitAvailability`로
  막아버려서 애초에 초과 상태로 개설되는 경로가 없다. "이미 개설된 후 타사
  한도가 늘어나서 뒤늦게 초과되는" 케이스를 감지해서 `benefit`을 IMPOSSIBLE로
  내리는 배치/서비스는 못 찾음 — 있다면 어디 있는지 담당자한테 확인 필요.
- **§3 골든 넘버(74.4%, 193.9만원) 재현은 불가능, 재현할 필요도 없음**: 실시간
  환율 API가 끼는 구조라 라이브로 그 숫자를 통제할 수 없다. 대신 실제 라이브
  데이터로 손계산과 API 응답이 항상 정확히 일치하는지를 검증하는 게 진짜
  의미 있는 확인이고, 오늘 전 구간에서 그렇게 확인함(위 "실측 결과" 참고).
- **세액 확정저장(`POST /api/tax/calculations/{id}`)엔 날짜 게이트가 없다.**
  CLAUDE.md §2의 "2027.5월 확정신고"는 실제 세법상 시점을 적어둔 것일 뿐,
  코드(`RiaTaxProperties`엔 `year`만 있음)는 아무 때나 호출을 막지 않는다.
  실제로 시스템 시각 2026-08-19에 정상 저장됨 — 의도된 설계인지 빠진 검증인지
  팀 확인 필요.
- **확정저장은 계좌 단위 API만 있고 일괄(bulk) 확정저장은 없다.** 세액 스냅샷
  배치(`/api/tax/snapshots/jobs`)는 한 번에 전 계좌(오늘 기준 373개)를 처리하는데,
  `POST /api/tax/calculations/{accountId}`는 계좌 하나씩만 처리 가능. 지금 시연
  목적으론 문제 없지만(계좌 1개 시연), 2027년 5월 확정신고 시즌 실제 운영에서는
  스케일 이슈가 될 수 있어 백로그로 남겨둘 만함 — 지금 당장 고칠 필요는 없음.

## seed-generator와의 관계

`db/seed/*.sql`(1만~3만 건 규모)은 목록·통계 화면을 채우는 **벌크 데이터**고, 이
런북은 **1개 계좌를 처음부터 끝까지 실제 API로 흘리는 라이브 시연**이라 서로 다른
용도. 다만 `seed-generator`가 계산 데이터(account/inbound/sell_order 등)까지
raw SQL INSERT로 만드는 건 CLAUDE.md §12("계산 데이터는 서비스 계층 호출로 생성,
랜덤 INSERT 금지")와 방향이 다르므로, 왜 그렇게 결정됐는지(성능/시간 제약 때문인지)
팀에 한 번 확인해보는 걸 권함 — 이번 작업 범위는 아니라 손 안 댔음.
