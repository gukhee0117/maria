## 슬라이드 1 — 이 파트가 왜 어려운가 (문제 정의)

- RIA는 "해외주식 매도차익에 대한 양도소득세를 한시적으로 감면"하는 제도.
- **가장 흔한 오해**: "감면율(1~5월 100%/6~7월 80%/8~12월 50%)을 세액에 곱한다" → **틀림.**
- 실제로는 감면율이 **세액이 아니라 "공제액"을 만드는 데** 쓰이고, 그 공제액을 과세표준에서 뺀 다음에야 세율(22%)을 곱한다.
- 여기에 "다른 계좌에서 해외주식을 다시 사면 혜택이 깎인다"는 **외부 계좌 감시** 로직까지 얽혀서, 5단계 공식이 필요해짐.

**발표 포인트**: 이 파트는 CRUD가 아니라 "정부 정책 문서를 정확한 산식으로 번역"하는 작업이었다는 점을 먼저 짚기.

## 슬라이드 2 — 세액 계산 5단계 공식

```
[1] RIA 내 매도금액 & 조정전공제액
    조정전공제액 = Σ(구간별 양도소득금액 × 구간가중치)
    가중매도금액 = Σ(구간별 매도금액 × 구간가중치)      ← [3]단계의 분모

[2] RIA 외 계좌 순매수금액 (전 금융기관, 연금/ISA/신탁 포함)
    순매수금액 = Σ(외부매수 × 가중치) − Σ(외부매도 × 가중치)

[3] 조정비율 = 1 − (순매수금액 / 가중매도금액)
    조정비율 ≤ 0 이면 최종공제액 = 0

[4] 최종공제액 = 조정전공제액 × 조정비율

[5] 최종세액 = (총 양도소득금액[비가중 원금액] − 기본공제 250만 − 최종공제액) × 22%
```

**핵심 함정 (발표에서 반드시 강조)**
> **1~4단계는 "가중치를 곱한 금액", 5단계(실제 세액)는 가중치 없는 진짜 번 돈(원금액) 기준.**

- 검증 예시(골든 픽스처): RIA 내 매도 5,000만(양도소득 3,200만) + 외부 순매수 1,100만 → 조정비율 ≈74.4%, 최종세액 ≈193.9만원 (RIA 미적용 시 649만원 대비 약 455만원 절감).
- 이 예시를 처음 재현할 때 실제로 숫자가 안 맞았던 사연은 슬라이드 4 참고.

## 슬라이드 3 — 계산 엔진 구조 (`TaxCalculator.java`)

- 순수 계산 클래스. **DB 접근 없음** — 입력(매도 lot 리스트, 세율 규칙, 외부거래 리스트, 세제혜택 상태)만 받아서 결과 DTO 하나를 돌려줌 → 배치와 실시간 조회(API) 양쪽에서 재사용.
- 금액은 전부 `BigDecimal`, 반올림 지점은 계산 경로마다 **딱 한 곳**(마지막에만 `setScale`).
- 분기 최소화 원칙: "세제혜택 배제" 계좌는 `if`를 여기저기 넣는 대신 **조정비율 하나만 0으로 만들면** 공제액도 세액도 자동으로 0이 됨 (연쇄효과 이용).

```java
BigDecimal adjustRatio = benefitExcluded
        ? BigDecimal.ZERO.setScale(RATIO_SCALE, RoundingMode.HALF_UP)
        : adjustRatio(weightedExternalAmount, riaSell.getWeightedSell());
```

**발표 포인트**: "계산 규칙이 바뀌어도 이 클래스 하나만 고치면 실시간 미리보기·배치 스냅샷·확정 저장 세 곳이 동시에 정확해진다" — 단일 진실 소스(single source of truth) 설계.

**추가 리팩토링 (2026-08-19)** — `purchaseCost`(취득원가 = 매수단가 × 매수시환율 × 수량) 계산식이 `aggregateRiaSell`·`buildLotDetails`·`buildPeriodBreakdown` 세 군데에 토씨 하나 안 틀리고 중복돼 있던 걸 `private BigDecimal purchaseCost(SellLotDTO lot)` 메서드 하나로 추출. 계산 규칙이 바뀔 때 세 곳을 따로 고치다 하나를 빠뜨리는 사고를 원천 차단 — 슬라이드 3의 "단일 진실 소스" 원칙을 계산식 레벨까지 한 번 더 적용한 사례.

## 슬라이드 4 — 트러블슈팅 하이라이트 (발표에서 "왜 어려웠는지" 보여줄 소재)

이 프로젝트에서 가장 "인터뷰에서 얘기할 만한" 부분. 각 항목은 **증상 → 원인 → 해결** 순.

| # | 증상 | 원인 | 해결 |
|---|---|---|---|
| 외부 순매수 음수 | 밖에서 팔기만 하면 조정비율이 1을 넘어 혜택이 늘어남 | 제도 취지는 "다시 사면 깎는다"이지 순매도가 보너스는 아님 | 순매수 합산 직후 **0에서 clamp** (`sum.max(BigDecimal.ZERO)`) |
| 조정비율이 뒤집힘 | `1 − round(a/b, 4)`와 `round(1 − a/b, 4)`가 다른 값을 냄 | `HALF_UP`은 0에서 멀어지는 방향이라 뺄셈으로 부호가 바뀌면 반올림 방향도 반대로 작동 | 나눗셈은 정밀도 12자리로 넉넉히 하고, **4자리 반올림은 맨 마지막에 한 번만** |
| `tax_rule` 조회 오염 | 기본공제(250만)·세율(22%)까지 거래일 기준으로 조회 | effective-dated인 건 감면율(구간가중치)뿐. 기본공제·세율은 "확정신고 시점의 한 값" | 조회 메서드를 **날짜 필터 있는 것 / 없는 것 둘로 분리** |
| 골든 시나리오 숫자 불일치 | 문서 예시(매수 2,000만/매도 1,000만)를 재현해도 순매수 1,100만이 안 나옴 | 검증 예시에 "매수/매도가 각각 어느 구간인지"가 안 적혀 있었음 | 매수 6~7월(80%), 매도 8~12월(50%) 로 구간을 못 박아야 재현됨 |
| `POSSIBLE→REDUCED` 오판정 | 매도 이력이 아예 없는 계좌가 REDUCED로 잘못 표시됨 | 매도 0건이면 `weightedSell=0`이라 조정비율이 **가드값 0**을 반환하는데, 이걸 `ratio < 1`로 판정하면 항상 참이 됨 | 판정식을 `Σ(순매수 × 가중치) > 0`으로 변경 — **가드값과 의미 있는 값이 같은 숫자일 때 조건문에 쓰면 안 된다** |
| 조기인출 추징 처리 | `tax_calculation`을 UPDATE로 고치고 싶어짐 | 금융/세무 도메인의 "정정"은 덮어쓰기가 아니라 **행 추가**(확정신고 행 + 조기인출추징 행 2개, 추징세액은 차액) | `basis_type`으로 행을 나눠 INSERT-only 유지 |

**발표 포인트**: "버그를 하나씩 고쳤다"가 아니라 "도메인 규칙을 코드로 옮길 때 생기는 함정의 패턴"으로 묶어서 말하면 훨씬 설득력 있음 — 예: "가드값과 의미값 혼동", "반올림 지점은 한 곳" 같은 원칙은 이 프로젝트 밖에서도 재사용 가능한 교훈.

## 슬라이드 5 — 데이터 구조: "확정 근거"와 "표시용 캐시"를 분리한 이유

세액계산 화면(관리자 목록)에 계좌마다 세액을 띄우려면 행마다 실시간 계산이 필요한데, 그러면 페이지 하나 열 때마다 무거운 쿼리가 계좌 수만큼 반복됨. 그렇다고 계산 결과를 `tax_calculation`(확정신고 근거 테이블)에 캐싱하면 "미리보기는 저장하지 않는다"는 원칙이 깨짐.

**해결 — 테이블을 아예 분리**

| | `tax_calculation` | `tax_snapshot` |
|---|---|---|
| 성격 | **확정 근거** (법적 증거) | **표시용 캐시** |
| 쓰기 방식 | INSERT only, 행 누적 (정정 시에도 새 행) | 배치가 매일 UPSERT, 계좌당 1행만 유지 |
| 키 | `(account_id, basis_type)` UNIQUE | `account_id` UNIQUE |
| 어디서 보이나 | 확정신고 내역 | 관리자 목록 화면 + **"OO 기준" 시각 표시** |

**발표 포인트**: 캐시를 도입할 때 원칙(§8-6 미리보기 저장 금지)을 완화한 게 아니라 **저장소 자체를 나눠서** 원칙과 성능을 둘 다 지켰다는 게 핵심. 단, "이건 캐시다"라는 걸 화면에서 반드시 드러내야(기준시각 노출) 원칙 위반이 아니게 됨 — 그래서 화면에 `산출시각`/`기준시각` 컬럼이 항상 붙어 있음.

**화면에서 실제로 지킨 방법 — "오래된 값" 태그**: 목록의 각 행마다 그 스냅샷의 `산출시각`(계산된 날짜)과 지금 시스템 시계가 가리키는 "오늘"(business clock)을 비교해서, 날짜가 다르면 `오래된 값` 배지를 붙임.

```js
function isStaleSnapshot(snap) {
    return !!businessToday && dateOnly(snap.calculatedAt) !== businessToday;
}
```

배치가 그날 아직 안 돌았거나 예전에 생성된 시드 데이터를 보고 있을 때, 관리자가 "이 숫자가 오늘 기준 최신인지"를 행 단위로 바로 구분할 수 있게 해줌 — 표 전체 헤더에 "기준시각"만 한 번 박아두는 것보다 한 단계 더 세밀한 신뢰도 표시.

## 슬라이드 6 — 세액 스냅샷 배치 (Spring Batch)

**문제**: 계좌 1만 건 전체의 세액을 매일 갱신해야 하는데, 계좌마다 개별 조회하면 1만 계좌 × 쿼리 2개 = **약 2만 쿼리**, 그중 외부 순매수 조회는 `target_product_judgement`(약 10만 행)를 매번 풀스캔.

**개선**: 계좌를 200건씩 chunk로 묶어 **일괄 조회(batch fetch)** — 페이지당 3쿼리 × 약 50페이지 = **약 150쿼리** (2만 → 150, 약 99% 감소).

```
Reader (AccountMapper, keyset 커서로 200건 페이징)
   → 그 200개 accountId로 매도lot·외부거래를 각각 "IN절 1쿼리"로 한 번에 조회
   → 계좌별로 그룹핑해서 완제품(TaxSnapshotTargetDTO)으로 버퍼에 채움
Processor (TaxCalculator만 호출, DB 접근 없음 — 순수 계산)
Writer (upsertSnapshots, ON DUPLICATE KEY UPDATE)
```

**설계 결정 근거 (Q&A 대비용)**

- **왜 Tasklet이 아니라 Chunk?** — 확정산 배치는 Tasklet이지만, 여긴 계좌 1만 건을 균일하게 반복 처리하므로 Chunk가 맞고 Reader/Processor/Writer 분리로 skip·재시작을 프레임워크가 대신 처리해줌.
- **왜 OFFSET이 아니라 keyset(PK 커서)?** — OFFSET 페이징은 조회 도중 계좌가 늘거나 줄면 행을 건너뛸 수 있음.
- **커서는 왜 "읽은 시점"이 아니라 "소비한(write된) 시점"에 전진?** — 버퍼를 채울 때 전진시키면, chunk가 버퍼 중간에서 커밋될 때 재시작이 이미 처리한 계좌를 건너뛰게 됨.
- **`calculatedAt`(업무시각)을 왜 Job Parameter로 고정?** — 페이지마다 시스템 시계를 다시 읽으면 한 번의 배치 실행 안에서 기준 시각이 흔들림.
- **실패 처리**: 계좌 하나가 이상해도 전체가 멈추면 안 되므로 `skip` 처리하되, `tax_rule` 자체가 없는 **설정 오류**라면 전 계좌가 실패하므로 skipLimit(100)을 넘기면 Job이 죽도록 함.
- **idempotent 보장**: 같은 날 배치를 두 번 돌려도 결과가 같도록 `ON DUPLICATE KEY UPDATE` 단일 문장으로 upsert (§8-4 배치 idempotency 원칙).

**발표 포인트**: "쿼리 수를 2만 → 150으로 줄였다"는 정량 수치가 있는 슬라이드라 발표 임팩트가 큼. Before/After 쿼리 카운트를 그래프로 넣으면 좋음.

## 슬라이드 6-1 — 배치 실행 이력 조회 (새 테이블을 안 만든 이유)

**요구사항**: 관리자가 "이 배치가 언제 돌았고, 몇 건 처리했고, 성공/실패했는지" 화면에서 확인할 수 있어야 함.

**흔한 접근**: `batch_history` 같은 이력 테이블을 새로 만들어서 배치가 끝날 때마다 INSERT.

**실제 선택**: 새 테이블을 만들지 않음. Spring Batch는 실행할 때마다 자기 메타데이터를 `BATCH_JOB_EXECUTION`/`BATCH_STEP_EXECUTION` 등 자체 테이블에 이미 기록해두는데, 이걸 Spring Batch가 제공하는 `JobExplorer`로 그대로 읽어서 DTO로 변환.

```java
// TaxSnapshotBatchHistoryReader — 새 테이블/새 저장 로직 없음, 조회만
List<JobInstance> instances = jobExplorer.getJobInstances("taxSnapshotJob", 0, 20);
for (JobInstance instance : instances) {
    for (JobExecution execution : jobExplorer.getJobExecutions(instance)) {
        // 실행별 readCount/writeCount/skipCount를 step들 합산해서 DTO로 변환
    }
}
```

`GET /api/tax/snapshots/jobs`로 노출, 화면에서는 최근 배치 요약(카드)과 "전체 이력 보기" 펼침 목록(페이지네이션) 두 단계로 보여줌.

**발표 포인트**: "이미 프레임워크가 갖고 있는 정보를 중복 저장하지 않고 재활용했다" — YAGNI 원칙의 실제 적용 사례. 새 테이블을 만들면 배치 성공/실패 시점마다 그 테이블에 쓰는 로직도 새로 만들어야 하고, Spring Batch 자체 메타데이터와 싱크가 안 맞을 위험도 생기는데 그 둘을 다 피함.

## 슬라이드 7 — 관리자 화면 (`/admin/tax`, PR #160)

**화면 구성 (위→아래)**

1. **KPI 카드 4개**: 전체 스냅샷 건수 / 과세대상(최종세액>0) 건수 / 세제혜택 일부감액·배제 건수 / 과세대상 최종세액 합계
   - **클릭하면 그 조건으로 목록이 바로 필터링됨** (예: "과세대상" 카드 클릭 → 최종세액>0인 계좌만 표시), 선택된 카드는 강조 테두리로 활성 표시. 검색어·세제혜택 드롭다운 필터와는 상호배타(하나 켜면 다른 건 초기화)라 "지금 무슨 조건으로 보고 있는지" 헷갈리지 않게 설계
2. **상세 패널**: 목록에서 행을 클릭하면 `/api/tax/preview/{accountId}`를 호출해 **그 순간 실시간으로 다시 계산**해서 5단계 공식 값을 전부 펼쳐 보여줌 ([1]~[5] 라벨을 그대로 화면에 노출)
   - **"배치값과 다름" 배지**: 방금 실시간 계산한 값과 배치가 어제 저장해둔 스냅샷 값이 다르면 경고 배지 표시 → 배치가 아직 최신 데이터를 못 따라잡았음을 관리자가 즉시 알 수 있음
   - **구간별 근거 표**: [3]단계 조정비율이 "왜 이 숫자가 나왔는지"를 구간(1~5월/6~7월/8~12월)마다 가중치·매도금액·양도소득·외부순매수로 쪼개서 보여줌 — 계산 결과 숫자 하나만 던지는 게 아니라 그 근거를 관리자가 직접 검산할 수 있게
   - **매도 내역 / 외부 순매수 내역 원장**: 종목(티커+상품명)·일자·금액 단위까지 내려가서 "이 계좌 세액이 이만큼 나온 건 결국 이 종목들 때문"을 추적 가능하게 함 (`TaxLotDetailDTO`/`TaxExternalTradeDetailDTO`)
3. **세액 스냅샷 목록 테이블**: 계좌번호/고객명, 세제혜택 상태(가능/일부감액/배제), 가중매도금액, 조정전공제액, 조정비율, 최종공제액, 최종세액, 산출시각. 검색(계좌번호/고객명), 정렬(최종세액↓/조정비율↑), 페이지네이션(10건/페이지)
4. **"배치 수동 실행" 버튼**: ADMIN/SETTLEMENT 권한만 노출. 클릭 시 `/api/tax/snapshots/jobs`로 배치를 비동기 트리거하고 감사로그(`TAX_SNAPSHOT_BATCH_REQUESTED`)에 기록.
5. **배치 실행 이력 카드**: 최근 배치 요약(처리건수/스킵건수/상태)을 상단에 항상 보여주고, "전체 이력 보기"를 펼치면 과거 배치들을 페이지네이션으로 조회 (슬라이드 6-1 참고)

**설계 포인트**

- 계좌 목록을 먼저 불러온 뒤, 그 accountId들로 스냅샷을 조회하는 2단계 구조. accountId가 많아지면 GET 쿼리스트링 길이 한도(브라우저/서버 제약)에 걸릴 수 있어 **200개씩 청크로 나눠 병렬 요청** (코드에 `ponytail:` 주석으로 "계좌 수가 더 늘면 POST 방식 API로 바꿀 것"이라고 한계와 다음 단계를 명시해둠).
- 권한 체크는 프론트(버튼 노출 여부)와 백엔드(`@PreAuthorize`) 이중으로 — 프론트는 UX용, 실제 방어선은 API.

**발표 포인트**: "화면 하나 안에 §3 공식 5단계가 그대로 라벨링되어 있다"는 점 — 발표 시연에서 계좌 하나를 클릭해 [1]~[5] 숫자가 실시간으로 뜨는 걸 보여주면 계산 로직 설명과 화면 데모를 한 번에 끝낼 수 있음.

## 슬라이드 8 — 성능: 일부러 나중으로 미룬 최적화 (측정 가능한 개선 사례)

- **현황**: 외부 순매수 조회 시 `target_product_judgement.ci_hash`에 인덱스가 없어 계좌 1건마다 약 7.5만 행 풀스캔. 인덱스를 넣어도 `WHERE YEAR(trade_date) = ?`처럼 **컬럼에 함수를 씌우면 인덱스를 안 탐.**
- **개선 계획 (2단계)**:
  1. `(ci_hash, trade_date)` 복합 인덱스 추가 → `YEAR()` 때문에 여전히 안 탐
  2. `YEAR(trade_date) = ?`를 범위 조건(`>= '2026-01-01' AND < '2027-01-01'`)으로 바꿈 → 그제서야 인덱스 사용, `EXPLAIN`의 `type: ALL → range` 확인 가능
- **왜 지금 안 고쳤나**: 미리보기 단건 조회는 체감이 없고 배치도 2~8분이면 끝나 블로커가 아님. **일부러 미뤄서 "측정 가능한 Before/After 성능 개선 사례"로 발표에 쓰려고 남겨둠.**
- ⚠️ 데모에서 배치를 수동 트리거로 실제 보여줄 계획이면 **발표 전에는 인덱스를 넣어둬야 함.**

**발표 포인트**: "인덱스가 없어서"보다 "인덱스를 넣어도 함수 때문에 안 타는 경우가 더 흔하다"는 걸 `EXPLAIN` 캡처(type 컬럼 변화)로 보여주면 실무형 소재로 강함.

## 슬라이드 8-1 — AI 코드리뷰(Copilot) 오탐 검증 사례

세액계산 관측성 강화 PR(#183)에 GitHub Copilot이 "머지 전 필수 확인" 항목 4개를 지적했는데, 실제 스키마·기존 코드 관례를 하나씩 대조해보니 **4개 다 이 프로젝트에서는 이미 방어돼 있는 상태**였음.

| Copilot 지적 | 실제 확인 결과 |
|---|---|
| `TaxMapper`가 `product_label`을 INNER JOIN으로 가져와서 데이터 누락 위험 | DDL 확인 결과 `sell_order.foreign_product_id`/`inbound_detail.foreign_product_id` 전부 `NOT NULL` + FK 제약. 이 쿼리 대상(`FINALIZED`+`EXECUTED`)은 정의상 반드시 그 체인이 존재해야만 생기므로 INNER JOIN이 행을 누락시킬 수 없음 |
| `TaxMapper`가 `Optional<TaxCalculationDTO>`를 반환하는데 MyBatis에서 지원되는지 불확실 | `grep`으로 세보니 `AccountMapper`·`AccountBenefitLogMapper`·`AdminMapper` 등 이미 10곳 넘게 쓰고 있는 **프로젝트 기존 표준 패턴** |

**발표 포인트**: AI 리뷰 도구는 프로젝트 고유의 스키마 제약이나 기존 코드 관례를 모른 채 일반론적인 위험만 나열하는 경우가 많다 — "AI가 지적했다"에서 멈추지 않고 DDL·기존 코드를 직접 대조해서 검증하는 과정 자체가 리뷰 소재. 슬라이드 4의 "가드값과 의미값 혼동" 같은 함정 패턴 발표와 묶어서 "검증 없이 넘어가면 안 되는 것"의 또 다른 예시로 쓰기 좋음.

## 슬라이드 9 — 업무 흐름상 이 파트의 위치

- CLAUDE.md 크리티컬 체인: `REGISTRABLE_STOCK API → B1(입고) → C1(매도접수) → C5(환전) → F2(세액계산) → E1(인출)`
- 즉 세액계산은 **매도·확정산이 끝난 뒤에만 의미 있는 값**이 나옴 — 매도 이력이 없는 계좌는 조정비율이 "가드값 0"이라는 게 위 트러블슈팅(POSSIBLE→REDUCED 오판정)의 근본 원인이었음.
- 세액 스냅샷 배치는 **확정산(00:00)·myData 동기화(01:00) 이후**(cron 02:00)에 돌아야 그날 데이터가 반영됨 — 배치 순서 자체가 도메인 제약.
- 데모 시나리오 5단계 중 1번("매도차익 있는 해외주식 편입 → 예상 감면세액 표시")과 직결되는 파트지만, **F7(사전 예상 세액 미리보기)은 아직 미착수** — 현재는 "매도 이후 사후 확정 계산"만 구현됨.
